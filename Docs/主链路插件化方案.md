# 小狼主链路插件化方案

更新日期：2026-10-14。状态：已选择 TypeScript＋Cordis 4 自行编写主链路，未开始实现。本文保留插件化原则和历史方案；最新完整功能与执行环节见 [主链路功能与执行流程](主链路功能与执行流程.md)。

## 0. 当前方案

用户已明确采用 TypeScript＋Cordis 4，参考 AstrBot、Koishi、ChatLuna、YesImBot 与 DeepSeek Harness 等实现，自行定义和编写小狼主链路。Cordis 管理插件与服务依赖；主链路及各能力按明确接口组合。基础库仍可复用，具体版本和依赖未选择。

当前只讨论功能与执行流程，不写代码、搭建骨架或引入依赖。流程、异常分支、能力接入和后续讨论顺序见 [主链路功能与执行流程](主链路功能与执行流程.md)。此前直接组装 Koishi＋聊天插件的建议转为历史参考。Koishi 当前核对版本依赖 Cordis 3，Harness 使用定制 Cordis 4，两者插件不假定直接可用。

以下 AstrBot 源码路线和职责映射保留为早期讨论记录，不代表当前实现决定。

## 1. 已确认目标

- 交付可独立构建、部署的完整小狼项目，使用 TypeScript＋Cordis 4 自写主链路，参考成熟实现并评估复用基础库。
- 主链路本身按插件思想组织，其他能力逐个增加、修改、替换或停用。
- 按需组合或精简基础能力；交付目标并非给用户现有的 AstrBot 增加外挂插件。
- 架构参考是 DeepSeek Harness；“Honeyse／Honeys”为语音转写，不另列为一个参考项目。
- 使用专用 NapCat，现有 AstrBot／NapCat 保持独立。机器人只在 NAS Docker 环境运行；NAS 写操作需用户审批。

## 2. 早期 AstrBot 源码路线建议（已暂停）

**建议克隆 AstrBot 后增量重构，保留成熟实现与上游来源。**

“直接改源码”可以包含调整模块边界和装配方式，不局限于配置或添加外围插件。主链路真正成为可替换插件，需要修改原有的启动装配和消息调度结构。

另一条路线是将 AstrBot 仅作为参考，选择性搬取实现，并重新建设小狼运行内核。它能获得更自由的结构，但提取会遇到生命周期、配置、数据库和全局对象之间的依赖，需要重新验证被拆开的行为。当前还没有足够依据证明这种成本低于增量重构。

源码核对基线为 AstrBot v4.28.2，提交 `3c7adafa1397e182d60b1016bf88759265113c8a`。这是当前参考基线，不表示已完成部署版本选择。当前源码由 `AstrBotCoreLifecycle` 集中初始化各管理器，`PipelineScheduler` 根据固定阶段顺序组织执行；不能将修改类名或添加一个事件监听器视为完成主链路插件化。

## 3. 早期 AstrBot 方案的职责映射（历史参考）

| 部分 | 职责 | 初期复用方式 |
| --- | --- | --- |
| 薄运行内核 | 读取组合配置、管理插件生命周期与依赖、注册和查找服务、分发事件。 | 收敛现有启动装配逻辑，仅保留必要运行职责。 |
| OneBot 接入插件 | 接收 NapCat 消息，转换消息事件，通过发送服务输出。 | 优先复用现有 OneBot 适配器和消息结构。 |
| 模型插件 | 提供统一模型请求与返回，处理接口差异。 | 复用现有模型提供者实现，先接 DeepSeek。 |
| 会话与存储插件 | 提供会话隔离、上下文读写及持久化服务。 | 复用已有会话、锁和存储实现，不预先重选数据库。 |
| 默认聊天插件 | 拥有一次回复的完整编排：触发、上下文与人设、模型／工具循环、发送和记录。 | 从现有消息处理与 Agent 流程收敛而来，保留成熟执行行为。 |
| 可选能力插件 | Memory、表情包、自学习、调度等，通过服务或明确事件接入。 | 按实际需求逐块评估复用、适配或自有实现。 |
| 管理界面 | 查看与配置已安装能力。 | 初期评估复用现有页面和接口；随底层边界调整。 |

以上为当时的职责映射，不要求每项单独打包发布，更不意味着每个插件单独运行一个容器或服务。当时沿用 Python 的建议现已暂停，当前采用 TypeScript＋Cordis 4 自写路线。

## 4. 借鉴 Harness 的具体内容

DeepSeek Harness 将能力的接口定义、提供者与消费者分开，插件向上下文注册服务与事件；智能体循环本身也可替换。小狼采用 Cordis 4 并借鉴这些可组合边界，不默认引入 Harness 的定制框架版本或完整运行时。

### 4.1 Cordis 与小狼的关系

DeepSeek Harness 基于 Cordis 插件框架；Cordis 提供共享上下文、服务与依赖、事件和生命周期管理，Harness 在其上以插件组合模型、工具、会话和 Agent loop。相关运行环境为 JavaScript／TypeScript 与 Node.js；官方 Python SDK 也通过启动 Harness 运行时工作，不代表 Cordis 是 Python 原生插件库。

小狼已确认 TypeScript＋Cordis 4，自行编写主链路；具体框架版本待原型验证。不自研插件内核，不把 Koishi 插件视为可直接加载，也不引入 Python 与 TypeScript 的桥接。

基础链路应由一组默认基础能力插件组成，其中聊天主链路插件负责串联接入、会话、模型与发送服务。内核只负责装配和生命周期；主链路内也不应把所有基础能力重新硬编码成一个不可替换的大模块。

用户进一步强调：成熟、通用指可支撑小狼后续模块的机器人基础能力。此前讨论过 AstrBot 改造与 Koishi 组装，现已选择自行编写。该方向不新增多平台兼容、第三方插件市场或复杂运行时等需求。

建议从第一版落实以下约束：

1. 插件通过声明的服务接口协作，避免直接读写其他插件的内部对象。
2. 默认聊天插件是当前回复编排的唯一负责人；替换它时，旧的默认聊天流程不得继续并行执行。
3. 普通消息先可供观察，再由聊天插件判断是否回复；不以回复过滤阻断后续收集能力。
4. 插件声明必要依赖，依赖缺失时给出明确错误；停用或替换时释放其监听、任务和资源。
5. 能列出插件及其启用状态、配置和错误；初期不预设插件市场、独立运行时或热更新需求。

真正的可替换性需要通过替换默认实现验证，不能仅靠把原有代码移入 `plugins` 目录认定完成。

## 5. 早期 AstrBot 实施顺序（已暂停）

1. 先列出源码保留、改造与延后裁剪的范围，并核实一次文本回复经过的调用路径。
2. 保留原有成熟实现，调整启动装配，定义必要的服务与插件生命周期边界。
3. 将现有聊天执行流程收敛为默认聊天插件，移除核心中的平行默认回复入口。
4. 对齐私聊默认回复、群 @／任意位置称呼触发、自身消息防循环及普通群聊旁路观察。
5. 在 NAS 的独立实例验收文本闭环、会话隔离、失败处理和重启持久化；再验证主链路替换与可选能力增减。
6. 实测依赖和资源占用后再裁剪无用功能，避免第一步盲目删除源码。

本方案未开始源码改造；NAS 只读检查已发现当前 SSH 身份无法访问 Docker socket，sudo 需要密码。没有修改 NAS 权限、目录、容器或服务。
