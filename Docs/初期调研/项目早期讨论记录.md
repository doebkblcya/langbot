> 历史归档，覆盖 2026-10-10 至 2026-10-14 的讨论。曾经确认或建议的旧路线不代表当前决定。当前以 [需求记录](../需求记录.md) 和 [主链路](../主链路.md) 为准。

### 5.1 AstrBot 阶段的主链路与插件化讨论（历史记录，2026-10-13）

当时用户确认采用 AstrBot 成熟链路，允许按需精简；主链路也视为可组合、可替换的能力，其余模块像积木一样逐步接入。随后用户提出 TypeScript／Koishi 新路线，本节方案已暂停；当前状态见第 5.3 节。

2026-10-13 补充澄清：用户要基于 AstrBot 成熟源码形成完整小狼项目，主链路作为小狼自身的内置插件。助手此前将交付物缩成“单独部署原版 AstrBot 后叠加小狼插件”的理解不符合目标，该交付路线已撤回。

当时助手建议：从锁定版本的 AstrBot 源码派生，保留来源、历史与许可证；小狼拥有自己的启动入口、构建镜像、配置和内置聊天插件，基础会话、人设、模型、工具循环与发送能力尽量复用成熟实现。先跑通文本闭环，再根据实际依赖收敛插件接口并精简功能。此源码路线现已暂停。

早期插件化方案已合并到本文后半部分：助手建议克隆后增量重构，真正调整启动装配与聊天流程边界；用户所说的 Honeyse／Honeys 为 DeepSeek Harness 的语音转写，不另列参考项目。该具体源码路线仍为助手建议。

待验证：AstrBot 原有消息管线并非整体可卸载插件。需要核实自有入口如何复用完整聊天执行流程，并保证默认回复与自有入口不会同时生成回复；插件化边界不能只靠改名或目录拆分认定已完成。

实施进度：已将 AstrBot v4.28.2（提交 `3c7adafa1397e182d60b1016bf88759265113c8a`）克隆到本地临时参考目录并阅读接入源码，未安装依赖、启动机器人或编写业务代码。NAS 仅做过只读检查。

模型核对来源：[DeepSeek 官方 API 入门](https://api-docs.deepseek.com/quick_start/pricing-details-cny/)、[模型能力说明](https://api-docs.deepseek.com/quick_start/pricing/)。

### 5.2 TypeScript／Koishi 优先调研（历史阶段，2026-10-13）

当时用户倾向 TypeScript，并明确允许直接复用 Koishi 及其基础插件组装小狼。已授权调研，未最终锁定版本或 ChatLuna；此组合路线现转为参考。九个功能模块、触发规则、统一人设与 NAS 部署约束不变。

当时助手建议优先验证 Koishi＋OneBot 适配器＋数据库与管理插件，ChatLuna 作为默认聊天／Agent 链路候选。核对的 Koishi 使用 Cordis 3，Harness 使用其定制 Cordis 4，不能因同源就直接混装。详细组合、代码证据、版本与未验证边界见 [Koishi 与 Cordis 底座调研](Koishi与Cordis底座调研.md)。

本轮只克隆临时参考源码、核对 npm 发布元数据并更新文档，未安装依赖、实现功能或部署。

### 5.3 TypeScript＋Cordis 4 自写主链路（当前方向，2026-10-14）

用户明确选择从头编写小狼，使用 Cordis 4 和 TypeScript，现有项目作为代码与机制参考；不再使用 Python。主链路自身为插件，其他能力按需接入。成熟网络、数据库和模型客户端库仍可评估复用，具体依赖未决定。

用户要求先调查路线问题，并按执行链路列出完整功能与细节，暂不写代码。已形成 [主链路功能与执行流程](../主链路.md)：启动接入、消息观察与触发、调度与上下文、模型／工具循环、发送与结算，以及异常、插件和后续模块接入。具体默认策略仍标为助手建议，按大模块继续讨论。

调查结论：路线可行，但 Cordis 4 当前候选仍带 RC 标记；Koishi／Harness 插件不能假定直接复用。会话并发、工具副作用、发送未知和生命周期需要自行定义和验证。没有把“快速原型”视为已具备成熟稳定性，也没有作固定工期承诺。本轮仅本地文档与只读调查，未安装、实现或部署。

随后用户要求提交、推送，并授权没有阻塞问题即可开始实现。已开始本地文字主链路，默认策略作为可改工程选择，未重新确认已知需求；未运行真实机器人或操作 NAS。代码与验证状态见 [实现进度](../实现进度.md)。

## 6. AstrBot 与 MaiBot 的初期拆解

以下是功能目录，不能据此认定对应源码可以独立搬运。同一行不一定表示等价功能。核心功能、可选能力和第三方插件的具体边界需按选定版本核对。

| AstrBot | MaiBot（麦麦） |
| --- | --- |
| 消息接入、过滤与触发 | 消息接入、发言时机与参与频率 |
| 会话与上下文管理 | 聊天上下文与历史回想 |
| 人设与回复生成 | 人设与回复生成 |
| Agent 规划与工具调用 | 行动规划与工具调用 |
| 文档知识库 | 长期记忆与人物画像 |
| 图片、语音等多媒体处理 | 图片、语音等多媒体处理 |
| 模型接入与管理 | 模型接入与管理 |
| 定时任务与主动消息 | 表达方式与黑话学习 |
| 插件扩展 | 表情包收集与选用 |
| 管理界面、配置与日志 | 行为学习与注意力机制（实验性） |
| — | 插件扩展；管理界面、配置与日志 |

初期核实到的情况：

- 两者核心后端均使用 Python；本次检查的 Agent 主流程均由项目自行组织，不能因为使用 FastAPI 等 Web 框架就认为 Agent 由该框架搭建。
- AstrBot 的内置 `ToolLoopAgentRunner` 负责模型与工具调用循环，也有外部 Agent 服务接入方式。
- MaiBot 的 `MaisakaReasoningEngine` 等核心流程负责行动规划与工具循环；表达学习、黑话学习、表情包管理有各自实现。
- MaiBot 当前有 A_Memorix 记忆子系统，其文档默认配置关闭。短期上下文、历史回想与长期记忆需要分开理解。
- MaiBot 的表达学习路径主要是提取、保存、选择表达材料供回复使用，不等于持续训练模型权重。
- MaiBot 当前 QQ 连接器与旧独立 NapCat 适配器的组织方式已有变化，研究时需避免混用旧教程。

助手判断：MaiBot 更值得研究拟人聊天、表达学习、表情包与记忆；AstrBot 更值得研究消息处理、模型接入、工具和扩展方式。这是研究方向建议，不是复用选型，也不是效果评测结论。

2026-10-11 补充：已将外部项目 LangBot 加入底座候选，详见 [LangBot 初期调研](LangBot初期调研.md)。它包含消息流水线、Agent、插件与管理能力，并有官方长期记忆插件可进一步评估。当前未决定采用，原有九个功能模块及已确认需求保持不变。

三者的历史对照与启动顺序见 [底座评估与启动建议](底座评估与启动建议.md)。当时助手建议先在 NAS 验证 AstrBot，LangBot 保留为替代候选，MaiBot 重点借鉴聊天机制；未部署。2026-10-14 已确定 Cordis 4 自写路线，当前方向见第 5.3 节。

## 2. 早期 AstrBot 源码路线建议（已暂停）

**建议克隆 AstrBot 后增量重构，保留成熟实现与上游来源。**

“直接改源码”可以包含调整模块边界和装配方式，不局限于配置或添加外围插件。主链路真正成为可替换插件，需要修改原有的启动装配和消息调度结构。

另一条路线是将 AstrBot 仅作为参考，选择性搬取实现，并重新建设小狼运行内核。它能获得更自由的结构，但提取会遇到生命周期、配置、数据库和全局对象之间的依赖，需要重新验证被拆开的行为。当前还没有足够依据证明这种成本低于增量重构。

源码核对基线为 AstrBot v4.28.2，提交 `3c7adafa1397e182d60b1016bf88759265113c8a`。这是当前参考基线，不表示已完成部署版本选择。当前源码由 `AstrBotCoreLifecycle` 集中初始化各管理器，`PipelineScheduler` 根据固定阶段顺序组织执行；不能将修改类名或添加一个事件监听器视为完成主链路插件化。

## 3. 早期 AstrBot 方案的职责映射（历史参考）

| 部分 | 职责 | 初期复用方式 |
| --- | --- | --- |
| 薄运行内核 | 读取组合配置、管理插件生命周期与依赖、注册和查找服务、分发事件。 | 收敛现有启动装配逻辑，仅保留必要运行职责。 |
| OneBot 接入插件 | 接收 NapCat 消息，转换消息事件，通过发送服务输出。 | 优先复用现有 OneBot 适配器和消息结构。 |
| 模型插件 | 提供统一模型请求与返回，处理接口差异。 | 复用现有模型提供者实现，先接 DeepSeek。 |
| 会话与存储插件 | 提供会话隔离、上下文读写及持久化服务。 | 复用已有会话、锁和存储实现，不预先重选数据库。 |
| 默认聊天插件 | 拥有一次回复的完整编排：触发、上下文与人设、模型／工具循环、发送和记录。 | 从现有消息处理与 Agent 流程收敛而来，保留成熟执行行为。 |
| 可选能力插件 | Memory、表情包、自学习、调度等，通过服务或明确事件接入。 | 按实际需求逐块评估复用、适配或自有实现。 |
| 管理界面 | 查看与配置已安装能力。 | 初期评估复用现有页面和接口；随底层边界调整。 |

以上为当时的职责映射，不要求每项单独打包发布，更不意味着每个插件单独运行一个容器或服务。当时沿用 Python 的建议现已暂停，当前采用 TypeScript＋Cordis 4 自写路线。


## 5. 早期 AstrBot 实施顺序（已暂停）

1. 先列出源码保留、改造与延后裁剪的范围，并核实一次文本回复经过的调用路径。
2. 保留原有成熟实现，调整启动装配，定义必要的服务与插件生命周期边界。
3. 将现有聊天执行流程收敛为默认聊天插件，移除核心中的平行默认回复入口。
4. 对齐私聊默认回复、群 @／任意位置称呼触发、自身消息防循环及普通群聊旁路观察。
5. 在 NAS 的独立实例验收文本闭环、会话隔离、失败处理和重启持久化；再验证主链路替换与可选能力增减。
6. 实测依赖和资源占用后再裁剪无用功能，避免第一步盲目删除源码。

本方案未开始源码改造；NAS 只读检查已发现当前 SSH 身份无法访问 Docker socket，sudo 需要密码。没有修改 NAS 权限、目录、容器或服务。
